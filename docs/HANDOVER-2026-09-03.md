## 1. Read this first — the environment is the blocker

Every slow or hung command this session traces to one cause, and it is not the code.

`npx eslint` failed with:

```
Error: ETIMEDOUT: connection timed out, read
    at Object.readFileSync (node:fs:442:20)
    ... node_modules/prelude-ls/lib/index.js
```

`readFileSync` returning **ETIMEDOUT** is a network-filesystem error, not a code error.

**Why:** the project sits at `~/Desktop/JCFarias`, iCloud Desktop-and-Documents sync
is enabled (`~/Library/Mobile Documents/com~apple~CloudDocs/Desktop` exists), and the
data volume is **95% full with ~11 GiB free**. Under disk pressure macOS evicts
iCloud-synced files to the cloud as *dataless files* — they look completely normal to
`ls` (no `.icloud` extension for Desktop/Documents sync since Big Sur), but any read
blocks until the file downloads, and can time out.

`node_modules` is tens of thousands of small files inside that synced tree. Every
`tsc`, `eslint`, `prettier` and `vitest` run walks it.

**Observed symptoms, all one cause:**

| Command | Result |
| --- | --- |
| `npm run lint` | Hung **56 minutes** at 0% CPU, state `S`, before being killed |
| `npm run typecheck` | No output after 180s+; killed |
| `npm run format:check` | Timed out at 120s on first attempt |
| `npx prettier --check` (scoped) | Completed, but took >90s |
| `npx eslint` | `ETIMEDOUT` on `readFileSync` |

A process at **0% CPU** is blocked on I/O, not computing. That is the tell.

### Fix this before resuming — pick one

1. **Move the project off the synced tree** (recommended, least invasive):
   `mv ~/Desktop/JCFarias ~/dev/JCFarias`, then `rm -rf node_modules && npm ci`.
   `~/dev` is not iCloud-synced.
2. **Free disk space.** 11 GiB on a 228 GiB volume is what is driving eviction.
   Getting back above ~15–20% free reduces it but does not eliminate it.
3. **Disable iCloud Desktop & Documents sync** (System Settings → Apple ID → iCloud →
   Drive → Desktop & Documents Folders). Heaviest hammer; affects the whole machine.

**Do not attempt to resume the plan before doing one of these.** Every task in the plan
ends with `npm run typecheck && npm run lint && npm run format:check && npm run test:run`.
All four walk `node_modules`. The run cannot make progress otherwise.

### This does not affect CI or Vercel

GitHub Actions and Vercel both build from a fresh checkout on local disk. Task 2's
workflow and Task 12's deploy are unaffected. This is purely a local-machine problem.

## 5. Changes made to the plan this session

The plan on disk is **newer than the version originally approved**. Differences:

**Two defects in the plan's own code, caught by pre-flight scan before any dispatch:**

1. `tsconfig.json` `"types"` originally omitted `"node"`. Specifying `types` at all
   disables automatic `@types/*` inclusion, so `@types/node` would have vanished and
   Task 9's `import { readFile } from "node:fs/promises"` would have failed to typecheck
   — eight tasks after the cause. Corrected to `["node", "vitest/globals"]`.
2. `app/opengraph-image.tsx` had a trailing comma inside parenthesized JSX
   (`</div>,\n)`) — a syntax error. Also replaced `<br />` with a nested flex column,
   since satori's `<br>` handling renders subtly wrong rather than failing loudly.

**Domain (D1):** 11 references `.co` → `.com`. Matched with a negative lookahead on the
dot so the GitHub repo slug `rfarias23/jcfarias-co` — a repo name, not a domain — was
left alone. (`jcfarias.co` is a substring of `jcfarias.com`; a naive replace yields
`jcfarias.comm`.)

**Task 12 Step 8 rewritten for GoDaddy specifically**, plus a new Step 8b:
- GoDaddy has **no apex CNAME/ALIAS/ANAME**, so the naked domain must be an **A record
  to `76.76.21.21`**, not the CNAME most registrars allow.
- A fresh GoDaddy domain ships with a parking `A` record on `@` and often a Domain
  Forwarding rule. **Edit the existing record, do not add a second one** — two A records
  round-robin between Vercel and the parking page, presenting as a site that works about
  half the time.
- Step 8b covers propagation and TLS. A certificate pending past ~15 min is almost
  always that duplicate A record, or a `CAA` record not permitting Let's Encrypt.

**Task 10:** Step 4 (stats) downgraded from gate to recorded confirmation. Step 2
(transaction record) marked BLOCKED. Added an explicit bar: **Task 12 must not deploy to
production while the transactions table still holds the six representative rows.**

## 6. Open question the next session must settle

`package.json` has `"lint": "eslint"` — a bare invocation with no file patterns. Under
ESLint 9 flat config this is suspect, and it is the command that hung for 56 minutes.

**It is not yet proven whether this is a genuine script defect or purely the iCloud
stall.** The `ETIMEDOUT` stack points squarely at the filesystem, so the filesystem is
the confirmed cause of *that* failure. Whether `eslint` with no arguments also lints
nothing (silently passing, which would be worse) is untested.

**Do this after fixing the environment, before trusting any green lint:**

```bash
npm run lint            # does it exit? how long?
npx eslint . --max-warnings=0   # compare — does it report more?
```

If bare `eslint` lints nothing, change the script to `eslint .` and note it. A lint step
that passes because it checked zero files is worse than one that hangs — CI would go
green while enforcing nothing, on every task in this plan.
